# cc-tooling

Claude Code を長く運用するうちに必要になった3つの仕組み。
どれも「**壊れたことに気づけない**」を潰すために作った。

- `hooks/` … コード変更後に検証を強制する Stop フック（監督AIゲート）
- `memory-index/` … memory を全文読みせず、事前分析した索引を引く（RAG化）
- `monitoring/` … 自動化の生死判定を JSON 1件の登録で付けられる登録簿

macOS + Claude Code 前提。実運用から切り出したもので、環境固有の値は除いてある。

---

## 1. hooks — 監督AIゲート

コードを変更したのに検証（テスト実行・独立レビュー）の痕跡が無いまま
「完了」しようとしたとき、**1回だけ差し戻す** Stop フック。

```jsonc
// ~/.claude/settings.json
{ "hooks": { "Stop": [ { "hooks": [
  { "type": "command", "command": "~/.claude/hooks/stop-verify-reminder.sh" }
] } ] } }
```

通す条件（いずれか）:
- テスト/構文チェックの**実行**（`pytest` / `node --check` / `bash -n` / `--dry-run` 等）
- Agent ツールで独立レビューを受ける
- code-review 系スキルの実行

### 設計上の要点（触る前に読む）

| 制約 | 理由 |
|---|---|
| headless（`claude -p`）では**絶対にブロックしない** | 無人実行がJSONを期待している場面で散文を返させると処理が壊れる。実際に本番の採点が2件失敗した |
| 差し戻しは**同一セッション1回だけ** | Stop の block はモデルを続行させるため、無条件だと無限ループになる |
| 状態ファイルは `$HOME` 配下 | `/tmp` は消える。消えると「1回だけ」が保証されない |
| 書けないときは**ブロックしない** | 判定不能で止め続けると作業が進まない（可用性を人質に取らない） |
| キルスイッチ | `hooks/off/stop-verify-reminder.off` を置くと全機能停止 |
| 検証痕跡は**最後のコード編集より後ろ**だけ見る | 編集前の Agent 起動を「検証済み」と誤認すると、調査で一度使うだけでゲートが素通りする |
| 編集ツール名と拡張子は**同一 tool_use 内で結合**して判定 | 別々に見ると `.py` を Read しただけで誤ブロックする |

`verify-gate-doctor.sh` で状態確認（`--fix` で settings.json への再登録）。

## 2. memory-index — memory のRAG化

memory が数百件になると毎回全文読むのが重い。**事前に構造化した索引**を引く形にする。

```bash
python3 build_index.py          # 索引を作る（type/topic/keywords/links を抽出）
./mem "アラートが鳴らない"       # 検索
./mem "API" --show 1           # 本文を表示（ここだけ全文を読む）
./mem --topics                  # トピック一覧
```

memory の置き場は `CC_MEMORY_DIR` で指定できる（未指定なら自動検出）。

### 任意: 意味検索（第2層）

```bash
python3 -m venv .venv && ./.venv/bin/pip install sentence-transformers numpy
./.venv/bin/python build_vectors.py
```

`multilingual-e5-small` によるローカル埋め込み。**APIキー不要・課金なし・外部送信なし**。
無くても第1層だけで完全に動く（`vectors.npz` を消せばキーワード検索に戻る）。

### 設計上の要点

- **トピックは出現場所で重み付ける**。素朴な部分一致だと本文の通りすがりの1語でタグが付き、
  実測で1トピックが全件の6割に付いて絞り込みに使えなかった。
  → ファイル名5点 / description3点 / 本文は出現回数（上限6）、計4点以上で採用。
- **意味点でキーワードの順位を壊さない**。重み1.5・上位20件のみに加点する。
  全件に薄く足すと無関係な候補に下駄を履かせて相対順位が崩れる。
- **索引の陳腐化を自動検知**する。件数のずれも見る（mtime だけでは**削除を検知できず**、
  消したメモリを現存として返してしまう）。
- 埋め込みは `name + description + 先頭行` のみ。全文は入れない。

## 3. monitoring — 生死判定の登録簿

「作ったのに監視が無い」を潰す。**JSON に1件足すだけ**で監視対象になる。

```bash
cp monitors.example.json monitors.json
python3 check_monitors.py          # 判定を表示
python3 check_monitors.py --json
```

```json
{
  "label": "com.example.nightly-job",
  "what": "夜間バッチ（毎日3:00）",
  "probe": ["file_mtime", "/path/to/logs/nightly.heartbeat"],
  "stale_hours": 30
}
```

同梱の probe は `file_mtime`（成果物の更新時刻）と `http`（WebAppの疎通、
`plist:<launchdラベル>:<環境変数名>` で URL 解決も可）。拡張は `evaluate()` に分岐を足す。

### 設計上の要点

- **痕跡（side effect）で判定する**。プロセスの有無ではなく「成果物がいつ更新されたか」。
  トリガー一覧が取れない環境でも実測できる。
- **「止まっている」と「対象が来ていない」を区別する**。区別できないときは断定せず
  「要確認」と言う。誤報は監視を殺す。
- **判定できないことを「正常」と言わない**。手段が無いものは `blocked` に理由を書いて
  「確認不可」として可視化する（放置ではなく記録）。
- **到達＝デプロイ生存**であって、中の処理が動いている証拠ではない。混同しない。
- **登録簿が壊れても監視は止めない**（警告して続行）。

### 作るときの作法

```bash
date +%s > "logs/<名前>.heartbeat"   # ★成功時のみ。失敗時に書くと誤判定になる
```

## 共通する考え方

この3つは同じ失敗から来ている。**「異常が異常として現れない」**という失敗。

- エラーが出ていない ≠ 動いている
- 終了コード0 ≠ 成功
- 痕跡が在る ≠ 生きている（3ヶ月前の心拍でも「稼働中」に見える）
- 収集できない ≠ 問題が無い（空の結果を「異常なし」と表示してしまう）

なので**番人自身を壊してテストする**。判定ロジックを1つ殺して、
ちゃんと落ちるか・赤が消えるかを確かめる。落ちない番人は番人ではない。
